## 4. Architectural Foundations Already Implemented

- **Auth**: bcrypt password hashing, JWT access tokens + rotating hashed refresh tokens (cookie + legacy bearer dual support), email verification gate (`AUTO_VERIFY` forced `false` in production regardless of env value), password reset flow, CSRF double-submit check on cookie-based refresh/logout. As of M38: `users.password_changed_at` (nullable) lets `middleware/auth.ts`'s `authenticate()` reject any JWT (legacy bearer or short-lived cookie access token) whose `iat` predates the user's most recent password reset — one narrow DB lookup added to the sole auth chokepoint; `login()` runs `bcrypt.compare` exactly once per attempt (against a dummy hash when the account doesn't exist) and throws one identical error for every failure case, closing an account-existence/verification-state + timing oracle; `resetPassword()`'s password update and refresh-token revocation are now one atomic transaction. See `docs/security/SECURITY_FINDINGS.md` §10 for the full credential-lifecycle table.
- **RBAC / team hierarchy**: `requireTeamRole`/`requireTeamMembership` middleware (`backend/src/common/middleware/requireTeamRole.ts`) gates routes by team role; service-layer hierarchy rules prevent non-owners from modifying an existing `owner`/`admin` (`teams.service.ts` — `removeMember`, `updateMemberRole`, `addMember`). As of M36, the hierarchy check for these three is enforced atomically inside the mutating SQL statement itself (`removeTeamMemberIfAuthorized`/`updateMemberRoleIfAuthorized`/`addTeamMemberIfAuthorized` in `teams.repository.ts`, each a conditional `DELETE`/`UPDATE`/`ON CONFLICT ... DO UPDATE ... WHERE`), not a separate read-then-write.
- **Resource-reference integrity (M39)**: `projectsService.validateTaskReferences` validates `tasks.owner`/`reviewer`/`contributors` against `projectsRepository.canAccessProject` (existence + same-project-team membership, any role) and `tasks.dependencies` against `tasksRepository.tasksExistInProject` (existence + same-project scoping) before every `createTask`/`updateTask`. `acceptInvite` (`teams.repository.ts`) is now one atomic conditional `UPDATE ... WHERE status = 'pending'` inside `withTransaction`, and `removeMember`/`leaveTeam` proactively revoke any still-pending invite for the departing member's email on that team.
- **Database error boundary (M40)**: `errorHandler.ts` now translates a narrow set of untranslated Postgres error codes (`23505` unique violation, `23503` FK violation, `22P02` invalid UUID syntax) into a safe `AppError` (`ConflictError`/`BadRequestError`) before falling back to the generic 500 — one choke point, not a per-repository try/catch. Every route with a UUID path param now validates it via `validateUuidParams(...)` (`common/middleware/validate.ts`, built on the existing `validate()` machinery) before any DB-touching middleware runs. `createTeam`, `removeMember`, and `leaveTeam` each run their multi-statement writes inside `withTransaction`. `team_invites`/`join_requests` carry a new partial unique index (`(team_id, email)`/`(team_id, user_id) WHERE status = 'pending'`) with `ON CONFLICT DO NOTHING` + a clean 409 on the service layer.
- **Database / migrations**: `node-pg-migrate` migrations in `backend/migrations/` (`Up`/`Down` SQL pairs), `database/schema.sql` kept in sync; `withTransaction` helper (`db/client.ts`) used for atomic multi-statement operations where present (`acceptInvite`, `approveJoinRequest`, `resetPasswordAndRevokeSessions`, and as of M40, `createTeam`/`removeMemberAndInvalidateInvites`/`leaveTeamAndInvalidateInvites`). **Note**: both the test DB and the main dev DB's schemas were set up directly from `database/schema.sql`, not via `node-pg-migrate up`'s incremental tracking (confirmed when M38's migration attempt tried to replay the entire migration history and hit a column-already-exists conflict on an unrelated, already-applied earlier migration) — new additive columns/indexes are applied directly via a one-off script against both databases instead, with the migration file kept for documentation/future-tooling consistency (M40's `1786251838274_add-pending-invite-join-request-unique-index.sql` was applied this same way, after directly querying both DBs first to confirm zero existing duplicate pending rows). Don't assume `npm run migrate:up` works cleanly against either database without checking first.
- **Read authorization / collection scope (M41)**: Every collection endpoint's result set is now scoped to a real invariant (own teams, own resources, or a deliberately-public discovery feature) with `GET /users` closing the one gap that had none — see `usersRepository.getAllUsers(callerId)`, scoped to "shares a team with the caller" via a `team_members` self-join. `GET /leaderboard` remains deliberately global/unscoped (a company-wide feature, not a gap — see `docs/security/SECURITY_FINDINGS.md` §13). `GET /logs/my`'s `?limit=` is now validated/bounded (`getMyLogsQuerySchema`, `[1,100]`, default 30) instead of a raw `parseInt(...) || 30`.
- **Fresh full-repo audit findings closed (M42)**: `POST /teams`/`POST /goals` now guard a client-supplied `parentTeamId`/`parentGoalId` at creation time (`requireTeamRoleIfSpecified(parentTeamIdFromCreateBody, ...)` / `canWriteGoal` reused in `goalsService.createGoal`), closing the same M29/M30/M35 cross-reference-authorization class recurring on the CREATE (not just UPDATE) path. `GET /blockers/:blockerId/ai-advice`/`GET /logs/{suggestions,insights,standup}` now each carry their own independent `createApiLimiter()` budget (previously unrated, repeatable AI-provider reads). `GET /projects/:projectId/tasks` batch-loads referenced users/tasks via two bulk `ANY($1)` queries (`usersRepository.getUsersByIds`, `tasksRepository.getTasksByIds`) instead of an O(N) per-task fan-out.
- **Write-side state-machine integrity (M43)**: `rejectInvite`/`approveJoinRequest`/`rejectJoinRequest` (`teams.repository.ts`) now guard on `status = 'pending'` in the same atomic-conditional-UPDATE style `acceptInvite` (M39) already used — closes a demonstrable state-inconsistency where rejecting/re-processing an already-accepted/approved/rejected invite or join request could flip its status against the real membership state. `blockers.affected_tasks` now validated for existence + same-team scoping (`tasksRepository.tasksExistInTeam`, a join through `projects`) on both create and update, matching the M39 pattern already applied to `tasks.dependencies`.
- **Goal-hierarchy cycle prevention (M45)**: `goalsRepository.wouldCreateCycle(goalId, candidateParentId)` walks the candidate parent's ancestor chain and rejects (`BadRequestError`) any `updateGoal` that would close a `parent_goal_id` cycle — closes a genuine, low-privilege-reachable DoS (an unbounded `WITH RECURSIVE` query in `calculateGoalProgress`, since `UNION ALL` never deduplicates). `calculateGoalProgress`'s CTE and `wouldCreateCycle`'s own ancestor-walk are BOTH independently hardened with the standard cycle-safe recursive-query idiom (a `visited` array in each row, `WHERE NOT (next = ANY(visited))`) as defense in depth. `teams.parent_team_id` was confirmed NOT to need the same fix — `getSubTeams` is a flat, non-recursive query, and `RECURSIVE` appears exactly once in the entire backend.
- **N+1/shared-pool amplification hardening (M46)**: `teamsRepository.searchTeams` capped at `LIMIT 50` and batch-loads owners/member-counts (`getUsersByIds`, new `getMemberCounts`); `logsService.getStandup` batch-loads every member's today-dated log via new `getTodaysLogsForUsers` (`log_date = CURRENT_DATE`, filtered in SQL not JS -- also fixes a genuine pre-existing timezone bug in the old JS-side date comparison); `blockersService.getTeamBlockers` batch-loads creators/message-counts (new `getMessageCounts`); `getMessages`/`getAIMentorAdvice` no longer re-fetch each message's author at all (`getBlockerMessages` already joins it); `teamsService.getMyInvites`/`getJoinRequests` batch-load teams/inviters/users (new `getTeamsByIds`). `goalsService.buildGoalTree` rebuilt around a precomputed `parent -> children` index (O(n) total instead of O(n²)). `jwt.ts` now names `algorithms: ['HS256']` explicitly on sign/verify (defensive hardening, not an active fix -- the library already refused `alg: none`).
- **`max_team_size` real enforcement (M47)**: previous milestones (M42/M44/M46) concluded it was decorative on the incorrect evidence that the frontend never surfaced it — `Teams.tsx`'s create-team form actually has a required "Team Size Limit *" field. `teamsRepository.addTeamMemberIfAuthorized`/`acceptInvite`/`approveJoinRequest` (the three membership-growing paths) now atomically gate their INSERT on `COUNT(*) < max_team_size`, each preceded by its own `SELECT ... FOR UPDATE` statement on the team's own row (a genuine race condition in a same-statement CTE "optimization" of this was caught by this milestone's own concurrency test and reverted — see `docs/security/SECURITY_FINDINGS.md` §19). `teamsRepository.isTeamAtCapacity` lets the service layer distinguish a capacity-block from a hierarchy-block for the right error message.
- **Connection pool / capacity tuning (M47)**: `utils/database.ts`'s pool gained `statement_timeout: 30000` (previously unset anywhere — a residual M45 flagged but didn't fix) and `connectionTimeoutMillis` raised from 5000 to 10000, based on direct, repeated measurement (bypassing all app code) showing real Neon connection-establishment times of 5.2-11.8 seconds. `backend/scripts/loadTest.ts` added as a reusable realistic-concurrency load-test harness.
- **Testing**: Backend — Jest + Supertest against a real `commandcenter_test` Postgres DB, 26 test files under `backend/tests/` as of M47 (adds `maxTeamSizeEnforcement.test.ts`, 12 tests). Frontend — Vitest + React Testing Library + jsdom (`frontend/vite.config.ts`'s `test` key), 4 test files under `frontend/src/` (15 tests). Always run `Get-ChildItem`/`ls backend/tests` to get the current count rather than trusting a number here.
- **CI/CD**: GitHub Actions pipeline at `.github/workflows/ci.yml`, Node 20 pinned, lockfiles tracked.
- **Logging / observability**: pluggable `LoggerProvider` abstraction (`backend/src/common/logging/`), structured logs with request IDs, security-relevant events logged without secrets/tokens.
- **Frontend error handling**: class-component `ErrorBoundary` (`frontend/src/components/ErrorBoundary.tsx`) using `getDerivedStateFromError`/`componentDidCatch` only, wraps the app root in `App.tsx`.
- **API/provider abstractions**: `AiProvider` (`modules/ai/providers/`), `EmailProvider` (`services/email/`), `LoggerProvider` (`common/logging/`), `RateLimitProvider` (`common/rateLimit/` — `createAuthLimiter()` [IP+email, login/register/forgot-password/resend-verification/reset-password], `createApiLimiter()` [per-user, independently wired into both `/api/ai/chat` and, as of M34, `POST /projects/analyze` — each call site gets its own separate budget, not shared], `createRefreshLimiter()` [IP-only, `/api/auth/refresh`, added M33]). All decouple `app.ts`/call sites from the underlying vendor library.

## 5. Security / Data-Integrity Fixes Completed (M24–M38)

- **M24** — `daily_logs` had no protection against a duplicate same-day log under concurrent requests (check-then-act race). Added a `UNIQUE(user_id, log_date)` migration (with a pre-check for existing duplicates) and translated Postgres `23505` into `BadRequestError('Log already submitted for today')` in `logs.service.ts`.
- **M25** — `acceptInvite` and `approveJoinRequest` (`teams.repository.ts`) could crash with a raw unique-violation 500 if the target was already a team member (e.g. joined via a second invite, or via an invite while a join request was still pending). Both now use `ON CONFLICT (team_id, user_id) DO NOTHING`, matching the pattern `addTeamMember` already had.
- **M26** — `POST /api/auth/resend-verification` returned distinct errors for "user not found" vs. "already verified," letting an unauthenticated caller enumerate registered/verified emails. Now mirrors `forgotPassword`'s pattern: one generic success response in all cases, while still actually resending the verification email to genuine unverified accounts.
- **M27** — `POST /teams/:teamId/members` let any team admin assign `role: 'owner'` (self-promotion) or silently overwrite an existing owner's/admin's role via `addTeamMember`'s `ON CONFLICT ... DO UPDATE`, since `addMember` had no hierarchy check unlike `removeMember`/`updateMemberRole`. Fixed by restricting the role enum at validation and applying the same owner/admin hierarchy rule before the repository call.
- **M28** — `privacy.service.ts`'s `updatePrivacySettings` computed the merged settings and returned them without ever writing to the database — a subsequent `GET` still returned the old values. Fixed by actually calling `usersRepository.updateUser`.
- **M29** — `PUT /projects/:projectId` let any non-viewer team member reassign a project's `team_id` to an arbitrary team with no membership check on the destination — the same class as `createProject`'s already-fixed guard, missed on update. Fixed by adding `requireTeamRoleIfSpecified` on a body-supplied `team_id`.
- **M30** — Same cross-reference pattern as M29, found in `goals.parent_goal_id`: `PUT /goals/:goalId` didn't validate a client-supplied parent goal's team. Fixed via `canWriteGoal` against the destination parent, plus made `calculateGoalProgress`'s recursive CTE team-scoped so a cross-team link (however it arose) can't pollute another team's aggregate.
- **M31** — Full-repo adversarial audit (not a code change). Produced ~30 findings across authentication, authorization, mass assignment, DB integrity, privacy, business logic, concurrency, API security, frontend/backend contract, and test quality. See the audit's own report (in conversation history) or `docs/security/SECURITY_FINDINGS.md` for the durable, reusable version. The single highest-severity finding (privacy settings persisted but never enforced) became M32.
- **M32** — M28 made `privacy_settings` persist, but nothing actually read `ai_enabled`/`leaderboard_visible` at their points of use. Added `privacyService.isAiEnabledForUser()`, checked at all 8 real AI entry points (log creation, chat, project analysis, blocker creation, mentor advice, log suggestions, log insights, standup) before calling the AI provider; added a `leaderboard_visible` filter to `leaderboard.service.ts`'s *returned* list only (not the query itself, which also drives a bulk `impact_score` refresh that must still run for hidden users — see `docs/security/SECURITY_FINDINGS.md` §3 for why filtering at the query layer would have been a regression).
- **M33** — `resend-verification`, `reset-password`, and `refresh` had no rate limiter at all, unlike `login`/`register`/`forgot-password`. `resend-verification` (has an email in its body) and `reset-password` (doesn't) were added to the existing `authRateLimiter` wiring — reset-password's key naturally degrades to IP-only, which is correct for a token-guessing threat model. `refresh` got its own new `createRefreshLimiter()` method (IP-only, 30/15min) since it's called automatically and frequently by every active session — the login limiter's threshold would false-positive normal usage. See `docs/security/SECURITY_FINDINGS.md` §6.
- **M34** — `POST /projects/analyze` called the AI provider with no rate limiter at all, the same "direct, repeatable, no-side-effect AI call" shape M22 fixed for `/api/ai/chat`, just under a route name that doesn't obviously read as an AI endpoint. Reused `createApiLimiter()` (not a new method — its abuse profile genuinely matches chat's) wired in independently, so it gets its own separate 20/5min budget. Verified via provider-call-count assertions (not just HTTP status) that a 429'd request never reaches the AI provider, that M32's `ai_enabled` check still fires before the provider call, and that CSRF/auth remain unaffected. See `docs/security/SECURITY_FINDINGS.md` §7.
- **M35** — `updateGoalSchema`/`updateTaskSchema`/`updateBlockerSchema`/`updateProjectSchema`/`updateTeamSettingsSchema` were all `z.record(z.string(), z.any())` — any body key reached the repository's `UPDATABLE_COLUMNS` allowlist unchecked. Replaced with explicit `.partial()` Zod object schemas (typed/enum/length-bounded fields only) for all five. Server-controlled fields (`completed_at` on goals/tasks, `resolved_by`/`resolved_at` on blockers, and the AI-derived `ai_suggestions`/`similar_blockers`/`suggested_helpers` on blockers) are no longer in any schema at all — Zod silently strips them, and the service layer now derives `completed_at`/`resolved_by`/`resolved_at` from the actual status transition (set on completion/resolution, cleared on reopen, so a reopened item never carries a stale timestamp). Also closed a newly-identified instance of the M29/M30 cross-reference-authorization gap: `teams.parent_team_id` (PUT `/teams/:teamId/settings`) had no destination-team check at all — added `requireTeamRoleIfSpecified(parentTeamIdFromBody, ['owner','admin'])`, same pattern as M29/M30. See `docs/security/SECURITY_FINDINGS.md` §8.
- **M36** — `removeMember`/`updateMemberRole`/`addMember` (`teams.service.ts`) each did a separate `getMemberRole` read, decided the owner/admin hierarchy rule in application code, then called a separate mutation with no transaction or lock between the two -- a concurrent role change on the same target could land in that gap and let the authorization decision act on stale data. Fixed by folding the check directly into the mutating SQL statement's `WHERE` clause (`removeTeamMemberIfAuthorized`/`updateMemberRoleIfAuthorized`/`addTeamMemberIfAuthorized` in `teams.repository.ts` -- a conditional `DELETE`/`UPDATE`/`ON CONFLICT ... DO UPDATE ... WHERE`), so Postgres's own row-locking makes the check-and-mutate atomic with no explicit transaction needed. Proved with a deterministic test that holds a real transaction lock open on the target row to force the exact interleaving the old code was vulnerable to, plus realistic `Promise.all` HTTP-level races. See `docs/security/SECURITY_FINDINGS.md` §4 (updated in place from "identified, not fixed" to the resolved pattern).
- **M37** — `GET /teams/:teamId/sub-teams` had only `authenticate`, letting any authenticated user retrieve any team's sub-team hierarchy (names, description, department, is_public/is_discoverable, etc.) just by knowing or guessing a team_id -- despite the route's own code comment always documenting "membership only" for this endpoint alongside its sibling `/members` route, which correctly had the guard. Added `requireTeamMembership(teamIdFromParams)`, the exact same middleware the sibling route uses. Deliberately did NOT reuse the `is_public`/`is_discoverable` team-discovery rule -- that governs a different question ("what teams can I discover") than this endpoint ("what are THIS team's sub-teams"), and applying it here would still let a non-member enumerate a private team's hierarchy once they had its ID. See `docs/security/SECURITY_FINDINGS.md` §9.
- **M38** — Three related M31 auth findings closed together: (1) `resetPassword()` revoked refresh tokens but had no way to invalidate an already-issued JWT (legacy 7-day bearer or short-lived cookie access token), both purely stateless before this milestone -- fixed with a new `users.password_changed_at` column compared against the JWT's own `iat` claim inside `authenticate()`. (2) `login()` short-circuited before `bcrypt.compare` for both nonexistent and unverified accounts while a verified account always paid the full bcrypt cost, and threw a distinct 403 for the unverified case -- both a timing oracle and a status/message oracle. Fixed: `bcrypt.compare` now runs exactly once per attempt (against a fixed dummy hash when the account doesn't exist), and every failure case throws the identical 401 `"Invalid credentials"`. (3) `resetPassword()`'s password update and session revocation are now one atomic `withTransaction` block instead of two separate statements, closing a real partial-failure gap. See `docs/security/SECURITY_FINDINGS.md` §10.

## 10. M48 — Multi-Context Workspace Architecture (Product Foundation)

**Status: design decision made, minimum P0 piece implemented, remaining scope deliberately deferred.** M48's own instructions were explicit that this milestone should determine the correct foundation first, not implement every future feature — this section is the actual deliverable; the code change is deliberately small.

### 10.1 Product/architecture inventory (what already exists)

- **`teams`** already has `parent_team_id` (self-referencing, confirmed non-recursive consumer — `getSubTeams` is a flat one-level query, re-confirmed M45/M46), a free-text `team_type` (`z.string().max(50).optional()`, default `'main'`, no enum anywhere, never branched on by any code path), a free-text `department`, and `is_public`/`is_discoverable` (M41/M46 confirmed: these gate *browsing/search* — `searchTeams`/`getAllTeams` — not membership or join-by-ID; `POST /teams/:teamId/join` has never checked either).
- **`users.role`** and the `authorize(...roles)` middleware that reads it are **dead**: `authorize` is imported by zero route files (grep-confirmed), `users.role` is set once at registration (`'member'`, DB default) and never updated by any repository method (`UPDATABLE_COLUMNS` in `users.repository.ts` excludes it). The JWT carries it (`decoded.role`) but nothing branches on that claim's value anywhere live. This is a genuinely unused, safely-repurposable column — see §10.4.
- **`team_members.role`** (owner/admin/manager/member/viewer) is the ONLY role that has live authorization consequences anywhere in the app, enforced exclusively through `requireTeamRole`/`requireTeamMembership` (`common/middleware/requireTeamRole.ts`). This is the resource-authorization layer M48 must not touch or duplicate.
- **`team_members.permissions`** (JSONB) is confirmed inert since M35/M40/M44 — never read by any authorization decision. Not touched by M48 either.
- **Join/invite mechanics** (`team_invites`, `join_requests`) are mature: atomic conditional status transitions (M39/M43), partial-unique-index duplicate prevention (M40), capacity enforcement (M47). `POST /teams/:teamId/join` already accepts any authenticated caller who knows a `team_id`, with NO privacy gate — i.e., **the "enter a Team ID to join" workflow Phase 6 asked about already works end-to-end at the request layer.** The only missing piece was letting a caller preview a team before firing a join request blind — see §10.3.
- **AI infrastructure** (`modules/ai/`) already has a provider abstraction (`aiProviderFactory`) and a generic, already-rate-limited chat endpoint (`POST /api/ai/chat` → `chatWithAI`) — the natural extension point for a future platform-helper bot (§10.6), not a new subsystem.
- **Privacy precedent**: `users.privacy_settings` JSONB (`ai_enabled`, `sentiment_tracking`, `leaderboard_visible`, `analytics_opt_in`) is the one existing per-user visibility-preference pattern in the codebase — the template to extend, not replace, if per-resource visibility levels are ever added (§10.7).

### 10.2 Multi-context/workspace model decision

Four models were compared (Workspace→Teams→Projects; Organization→Workspace→Teams→Projects; Context→Teams→Projects; extend existing Team via a type/context system). **Decision: Model D — extend the existing `teams` table, do not introduce a new top-level entity.**

Rationale, from the inventory above: `teams.parent_team_id` already provides a working, non-recursive hierarchy, and `teams.team_type` already provides a free-text categorization slot — a "Subject/Classroom" or "Hackathon" is representable *today*, with zero migration, as a `team` with `team_type = 'classroom'`/`'hackathon'`, whose constituent project-teams are its `parent_team_id`-linked children. This means:
- Every authorization mechanism (`requireTeamRole`, `requireTeamMembership`, capacity enforcement, invite/join-request flows) works on a "classroom" or "hackathon" **unchanged** — there is no second authorization system to build or keep in sync.
- Models A-C (a new `workspaces`/`organizations`/`contexts` table sitting above `teams`) would require a parallel membership table, a parallel authorization check, and a migration path for every existing team to belong to some default workspace — real migration risk and real duplicated logic, for a capability the existing hierarchy already provides.
- The one thing Model D does NOT solve for free: `team_type` has no validated enum today, so nothing stops `'clasroom'` (typo) or an arbitrary string from being stored. **Deliberately not fixed in M48** — introducing an enum now, before any consumer branches on the value, would be exactly the kind of premature constraint M40's `permissions: z.any()` precedent already warns against (inventing structure with no consumer yet). Revisit when a real feature (e.g., a classroom-specific dashboard) needs to filter/branch on `team_type` server-side.

### 10.3 Team discovery / join-by-ID model

**Implemented (the one concrete M48 code change):** `GET /teams/:teamId/preview` — authenticated, no membership/role/discoverability gate (matching `requestJoin`'s existing precedent), returns a narrow, deliberately safe field set (`team_name`, `description`, `team_type`, `department`, `is_public`, `is_discoverable`, `max_team_size`, `member_count`, `owner.{full_name,username}`, `created_at`) — no member list, no `permissions`, no `parent_team_id`, no tasks/projects/goals/blockers. Verified this adds no new exposure: a caller who already has a `team_id` could always `POST .../join` sight-unseen (zero privacy gate, unchanged since early milestones); this endpoint only lets them see the same shape of information `searchTeams` already exposes for discoverable teams, before committing to a join request, for a team that isn't necessarily discoverable at all. Six new tests (`teamPreview.test.ts`) cover: safe-field shape, exclusion of member-only fields, working against a private/non-discoverable team (proving the precondition), accurate `member_count`, 404 on a nonexistent team, 401 unauthenticated.

**Enumeration risk:** unchanged from M44's existing conclusion — `gen_random_uuid()` v4 IDs (~122 bits of entropy) make guessing a valid `team_id` infeasible; this endpoint doesn't change that calculus since `requestJoin` already had the identical exposure.

### 10.4 Persona vs. resource-authorization-role model (decision, not implemented)

**Decision: distinguish persona from role by repurposing the already-dead `users.role` column — but defer actually wiring it up.** `users.role` has zero live authorization effect today (§10.1) — it is JWT-carried but unread by any authorization decision, since `authorize()` is dead code. This makes it a safe, zero-migration home for a future "platform persona" label (`student`, `subject_coordinator`, `team_leader`, `hackathon_organizer`, `manager`, `company_manager`) **without ever touching `team_members.role`**, the one role that actually gates anything. A person's persona would answer "what onboarding/UX did they pick," while their `team_members.role` in any given team continues to answer "what can they do in THIS team" — exactly the separation Phase 5 asked for, with no new authorization system.

**Deliberately not implemented in M48**: wiring this up means deciding the actual onboarding UX (Phase 13, explicitly told not to build yet) and a values list for the persona field — doing that now would be guessing product requirements, the same discipline this project has applied to `permissions: z.any()` and `max_team_size` before real evidence existed. Recommended concretely for M49+: add a nullable `users.persona` column (or repurpose `users.role` directly, avoiding a migration entirely) once the onboarding flow that sets it is actually being built, not before.

### 10.5 Subject-coordinator and multi-team-manager models (decision, not implemented)

Both map cleanly onto the same primitive: **a coordinator/manager is a member (with an appropriate `team_members.role`, likely `admin` or a new-in-name-only tier) of the parent "classroom"/"program" team, and separately NOT automatically a member of every child team** — `team_members` rows are per-team by construction, so membership in a parent team_type='classroom' team grants zero implicit access to its children's own `team_members`-gated resources (tasks/goals/blockers/logs), unless the coordinator is ALSO explicitly added to each child team. This is the correct default (no silent "teacher sees everything" bypass, matching Phase 7's explicit instruction) and requires no new authorization concept — only a decision (deferred to M49+, needs real UX input) on whether a parent-team role should optionally cascade limited *read* access to children, which would need its own explicit, auditable mechanism (e.g., a `requireTeamRole` variant that also checks `parent_team_id` chains) rather than an implicit bypass. Do not implement this cascade without a concrete product requirement — the current default (explicit per-team membership only) is the safe one to ship without it.

### 10.6 Daily-work-logging + AI-summary + platform-helper roadmap (decision, not implemented)

The existing `daily_logs` table + `logsService.createLog` (one entry per user per day, enforced via a real unique constraint since M24) is the wrong shape for "many small entries through the day → AI summary → user edits → confirms" — that workflow needs multiple raw entries per day, not one. **Recommendation, not implemented**: a new `daily_log_entries` table (raw timestamped entries) feeding into the *existing* `daily_logs` row as the "confirmed summary" once the user submits — extending, not replacing, the current table, and reusing the exact `analyzeLog`-style AI-service pattern (a `generateCompletion` call behind the existing `aiProvider` abstraction, gated by the existing `privacy.ai_enabled` check). This needs its own migration and its own milestone — not attempted here, per Phase 9's explicit "do not implement yet unless the architecture clearly supports it," which it does not yet (no raw-multi-entry table exists). The platform-helper bot (Phase 11) should reuse the existing `POST /api/ai/chat` provider/rate-limit path, not a new AI subsystem — and per its own explicit security rule, must only ever describe existing UI/navigation, never perform an action itself (no new "assistant can call backend APIs on the user's behalf" capability should be added without its own dedicated authorization review).

**Model B selected: explicit coordinator capability on the parent context, narrowly scoped to read-only AGGREGATE child-team data (counts/booleans only, never content).** Compared against Model A (explicit membership in every child team — already works, doesn't scale), Model C (a separate coordinator-relationship table — solves nothing B doesn't, at permanent extra cost), and Model D (widening `team_members.role` itself — rejected outright, would conflict with the milestone's own "must not overlap `team_members.role`" instruction). **The critical distinction from a parent→child cascade:** the new endpoint (`GET /teams/:teamId/context-dashboard`) is gated by the SAME pre-existing `requireTeamRole` check every owner/admin route already uses, on the team the URL actually names (the parent). Nothing about being owner/admin of a parent grants access to any of a child team's OWN endpoints (`/blockers`, `/tasks`, `/work-entries`, `/members`, etc.) — those remain gated exactly as before, verified by a dedicated test using a coordinator with zero relationship to the target child team, confirming `403`. The dashboard is the one place a fixed, narrow set of counts becomes visible; content (titles, messages, member lists, work-entry text) never does.

### 13.2 Dashboard data model

Per child team: `member_count`, `submitted_today` (boolean), `open_blocker_count`, `task_progress` (`{total, completed, percent}` or `null` if no project exists yet), `needs_attention` (a transparently-derived boolean — `open_blocker_count > 0 OR (has members AND !submitted_today)` — never a hidden score; the raw signals it's derived from are also returned). Context-level summary: `total_teams`, `submitted_today_count`, `blocked_count`, `needs_attention_count`. No "hardworking score," no ranking, no per-person breakdown — the milestone's own explicit anti-surveillance constraint, honored by construction (the underlying queries never group by user, only by team).

### 13.3 Exact backend change

New module `backend/src/modules/contextDashboard/` (`contextDashboard.{repository,service,controller,routes}.ts`), wired into `routes/index.ts`. Four bulk queries (`WHERE team_id = ANY($1)` / `GROUP BY team_id`) regardless of child-team count — member counts, today's-submission set, open-blocker counts, task-progress counts — plus one query for the (LIMIT-200-capped) child-team list itself. No AI-provider call anywhere in this feature.

### 13.4 Frontend change

`frontend/src/pages/Teams.tsx`: when the caller's own role on the SELECTED team (already loaded via the existing `getTeamMembers` call) is `owner` or `admin`, fetch and render the new dashboard (summary tiles + per-team cards) in place of M50's plain sub-teams list; a plain member/viewer continues seeing exactly M50's existing (unchanged) sub-teams view. The frontend never decides who "is a coordinator" for security purposes — it only decides whether to ATTEMPT the request, and the backend's own `requireTeamRole` is what actually enforces access either way.

### 13.5 Deferred (documented, not implemented)

- **Filters/sorting on the dashboard** (all teams / needs attention / blocked / etc.) — the milestone's own instructions treat this as optional ("if practical"); deferred since the current classroom/hackathon scale (tens of teams, not hundreds) doesn't yet demonstrate a need, and the underlying data already supports adding it client-side later with no backend change.
- **"Last activity" timestamp per team** — would need a UNION across `daily_work_entries`/`tasks`/`blockers` update timestamps, a materially more expensive query than the 4 bulk queries this milestone uses; deferred until there's a demonstrated need, rather than adding query cost for a "nice to have" column.
- **Pagination UI for contexts with more than 200 child teams** — the backend already caps at 200 (defense against an unbounded aggregation surface); no context has approached this scale yet, so a paginated UI wasn't built ahead of that need.

## 15. M53 — Personal Daily Work History

**Status: VERIFIED / COMPLETE / CLOSED, pushed.** Extends M52's Daily Work flow from today-only to the caller's own past confirmed submissions, on `Pulse.tsx`, with exactly one new backend endpoint.

### 15.1 Design decision — Option B (dedicated personal-history read path)

Two options were compared: (A) extend the existing `GET /teams/:teamId/work-submissions` to accept a date range, vs. (B) add a new, dedicated endpoint scoped to the caller's own history. **Decision: Option B.** Extending the existing team-wide endpoint would have meant returning every teammate's confirmed-work content across many dates in one call (far more teammate content exposed than a "personal" feature needs, with privacy enforced only by client-side filtering) and risked changing the contract every existing caller (`Teams.tsx`, M52's own already-submitted check) depends on. Option B reuses the exact `GET /work-entries/today`-style shape (query-param `teamId`, `requireTeamMembership` gate) already established in the same module, with privacy enforced at the query layer (`WHERE user_id = $1` where `$1` is always `req.user!.userId`, never client-supplied) rather than by trusting frontend filtering. `GET /teams/:teamId/work-submissions` itself was **not modified** — confirmed byte-for-byte unchanged in the diff.

### 15.2 Exact backend change

New route `GET /work-entries/history?teamId=&limit=` in the existing `backend/src/modules/dailyWork/` module (one new method each in `.repository.ts`/`.service.ts`/`.controller.ts`/`.routes.ts`, one new Zod schema in `.dto.ts` — `workHistoryQuerySchema`, `limit` bounded `[1,30]` default 30, matching `getMyLogsQuerySchema`'s existing bounding convention). Query: `SELECT work_date, confirmed_summary, confirmed_at FROM daily_work_submissions WHERE user_id = $1 AND team_id = $2 ORDER BY work_date DESC LIMIT $3` — deliberately excludes `ai_summary`/`submission_id`/`user_id`/`team_id` from the response (smallest field set the UI needs). Gated by the existing `requireTeamMembership(teamIdFromQuery)`, unchanged.

### 15.3 Exact frontend change

`frontend/src/services/api.ts`: new `getWorkHistory(teamId, limit?)`. `frontend/src/pages/Pulse.tsx`: a collapsed-by-default "View past submissions" toggle inside the existing Daily Work section — history loads only on first expand (a `historyLoaded` guard prevents refetching on repeated toggling), fully independent of M52's today-state, and resets/collapses on every team switch (no cross-team leakage). `confirmed_at` is deliberately not displayed in the history cards (only `work_date` + `confirmed_summary`) — a minor, non-mandated implementation choice consistent with the minimal-field design.

### 15.4 Security testing

8 new backend tests (`dailyWork.test.ts`): own-history retrieval, cross-user isolation (another member's rows never appear, seeded via a direct `testPool` insert since the real submit API always writes `CURRENT_DATE`), cross-team isolation, non-member → 403, unauthenticated → 401, empty result, multi-record newest-first ordering, `limit` honored. 8 new frontend tests (`Pulse.test.tsx`): collapsed by default/no premature call, no call before team selection, opens and fetches on click, empty state, multiple records with correct date display, team-switch reset/no leakage, error handling, non-interference with M52's today flow.
